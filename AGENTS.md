# Быстрый вход в репозиторий

«Зачем я здесь?» / Why am I here? — локальное приложение для KDE Plasma 6
(Wayland) и Windows 10/11: спрашивает цель открытия программы, показывает
таймер и завершает сессию выбранным способом. Rust (stable, edition 2021),
UI на fltk-rs, без сервера и без сетевых запросов.
Общайся с пользователем на языке его запроса, обычно по-русски.

Ключевые требования к проекту: низкое потребление памяти (лёгкий фоновый
демон, окна только по требованию) и одинаковое поведение на обеих платформах.

## Текущий этап

Реализованы основа workspace и безопасный деморежим: движок сессий,
структура настроек и история целей в памяти, версионированный IPC,
часы с учётом сна, отдельные fltk-rs процессы для четырёх экранов.
`--demo --show` открывает настройки только текущей демонстрации.
UI использует тёмную компоновку: панель настроек с демосписком, компактная
форма цели и перетаскиваемая панель сессии. В UI время задаётся в минутах
(по умолчанию 15), внутри движка и IPC — в секундах. IPC имеет версию 3.
Работают пресеты 5/15/30 минут, визуальное предупреждение и досрочное
завершение демосессии. По кнопке загружается каталог установленных программ
(Linux: XDG desktop entries; Windows: Get-StartApps), с поиском в отдельном
окне. Каталог и звук обслуживает демон; UI получает записи по IPC порциями.
Звук выключен по умолчанию: встроенный assets/warning.wav, pw-play в Linux, PlaySoundW в Windows.
Элементы неготовых платформенных функций недоступны
и объясняют причину в подсказках; не выдавай демонстрационные данные за реальные.
Обычный запуск, `--show` и `--background` без `--demo` пока возвращают ошибку.
Далее описана целевая архитектура: KWin/Win32-бэкенды, трей, единственный
экземпляр, сохранение настроек, автозапуск и интеграционные тесты
ещё предстоит реализовать. Каталог `kwin/` пока отсутствует.
Бюджет памяти — целевое требование; выполнение нужно измерять на релизной сборке.

## Архитектура

Один исполняемый файл `why-here`, два режима:

- `why-here` — **демон**: трей, отслеживание окон, таймеры, блокировка,
  закрытие окон, завершение процессов, звук. Своих окон не создаёт.
- `why-here ui <экран> …` — **UI-процесс** на fltk. Его запускает демон,
  когда нужно показать окно; после закрытия окна процесс завершается.

Демон и UI общаются через stdin/stdout дочернего процесса: одна строка JSON
на сообщение. Типы сообщений определены в `core::ipc`, у протокола есть поле
`version`. UI не трогает окна других программ и не завершает процессы:
это делает только демон.

Поток исполнения: ОС/KWin → `platform::WindowBackend` → `daemon` → `core::Engine`;
демон применяет команды движка через бэкенд и запускает UI при необходимости.
Идентификатор приложения: `org.local.WhyHere` (`core::APP_ID`).

## Карта кода

| Путь | Ответственность |
| --- | --- |
| `crates/core/` | `Engine`, `Session`, идентификация приложений, таймеры, настройки, история целей, i18n, протокол IPC. Без ОС-зависимого кода, без GUI, без `unsafe` |
| `crates/platform/` | `trait WindowBackend`; `kwin.rs` (`cfg(target_os = "linux")`), `win32.rs` (`cfg(windows)`); дерево процессов и их завершение; список установленных программ; автозапуск; звук; монотонные часы с учётом сна |
| `crates/daemon/` | Цикл событий, трей (`ksni` на Linux, `tray-icon` на Windows), запуск UI-процессов, единственный экземпляр |
| `crates/ui/` | fltk-rs: форма цели, напоминание, настройки, выбор программы, тема |
| `crates/app/` | `main.rs`: разбор аргументов, выбор режима |
| `kwin/bridge.js` | KWin-скрипт: снимки окон и команды через D-Bus `Exchange` |
| `assets/` | Иконки, `warning.wav` |
| `.github/workflows/` | Проверки на `ubuntu-latest` и `windows-latest`, релиз по тегу |

## Инварианты, которые важно сохранить

- Все окна одной программы делят сессию; программы имеют независимые таймеры.
- До ответа на форму таймер не запущен. В режиме закрытия окон форму нельзя
  отменить; в режиме kill её закрытие завершает отслеживаемую программу.
- Режим завершения фиксируется при старте сессии.
- Таймер учитывает сон компьютера: на Linux `CLOCK_BOOTTIME`, на Windows
  `QueryInterruptTime` (не `QueryUnbiasedInterruptTime`). Не используй
  `std::time::Instant` для длительности сессий.
- Удаление/отключение отслеживания и выход из утилиты отменяют сессии без
  завершения отслеживаемых программ. Закрытие окна настроек закрывает только UI.
- Настройки пользователя не должны теряться между версиями: новые поля
  `settings.json` добавляются с `#[serde(default)]`, а переименование или
  удаление полей сопровождается миграцией.
- Не обрезай `.desktop` у обычного ID без разбора: это может быть часть имени.

### Завершение процессов — защиту не упрощать

- Процесс фиксируется до проверки: на Linux pidfd, на Windows открытый
  `HANDLE` процесса. Сигнал/`TerminateProcess` отправляется только через
  зафиксированный дескриптор, никогда по голому PID.
- Потомок принимается, только если время старта родителя совпадает
  (Linux: поле starttime из `/proc/<pid>/stat`; Windows: `GetProcessTimes`).
- Никогда не убивать: собственный процесс и его предков, процессы, связанные
  с окнами других отслеживаемых программ, системные процессы.
  Linux: `kwin_wayland`, `kwin_x11`, `plasmashell`, `Xwayland`, `dbus-daemon`,
  `dbus-broker`, `systemd`. Windows: `explorer.exe`, `dwm.exe`, `csrss.exe`,
  `winlogon.exe`, `ApplicationFrameHost.exe`, процессы сессии 0.
- Не ищи процессы по имени исполняемого файла и не отправляй сигналы группам процессов.
- Сначала завершаются потомки, затем корни.

### Особенности платформ

- **KDE:** окна UI должны иметь `app_id` `org.local.WhyHere`
  (`set_xclass` в fltk), иначе `bridge.js` не найдёт форму. Сборка с фичей
  `fltk/use-wayland`. Поиск формы в скрипте идёт по заголовку — при изменении
  заголовков окон обнови `bridge.js` для обоих языков.
- **Windows:** хуки `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` работают только
  в потоке с циклом сообщений; трей и таймер живут в том же потоке.
  Перед запуском UI демон вызывает `AllowSetForegroundWindow(pid)`.
  Окна UWP принадлежат `ApplicationFrameHost.exe`: настоящий процесс берётся
  из дочернего окна `Windows.UI.Core.CoreWindow`. Окна процессов с повышенными
  правами (UIPI) не блокируются — UI показывает, что ими нельзя управлять.

## Правила кода

- `unsafe` допустим только в `crates/platform`. Каждый блок — с комментарием
  `// SAFETY:`. `HANDLE`, `HWINEVENTHOOK`, pidfd и подобные ресурсы
  оборачиваются в RAII-типы с `Drop`.
- Платформенный код подключается через `#[cfg]`; `core` и `ui` собираются
  на обеих ОС без изменений.
- Без `tokio`: демону хватает потоков и каналов (`std::sync::mpsc`),
  `zbus` — через blocking API.
- Без `unwrap()`/`expect()` в демоне вне тестов: ошибка одного окна или
  процесса не должна ронять демон. Ошибки — `anyhow` в `app`/`daemon`,
  `thiserror` в библиотечных крейтах.
- Новые пользовательские строки — через `tr()` с русским исходным текстом
  и английским переводом в `core::i18n`. Смена языка применяется после перезапуска.
- Версия берётся из `[workspace.package]` в корневом `Cargo.toml`.
- Форматирование: `rustfmt.toml` с `hard_tabs = true` (табы, как в `.editorconfig`);
  два пробела в YAML; UTF-8 и LF.

## Бюджет памяти

Демон в простое — не больше 8 МБ RSS, без активности CPU при отсутствии сессий
(работа по событиям, тик раз в секунду только при активных сессиях).
UI-процесс — не больше 15 МБ, пока открыт. Изменения, которые заметно
увеличивают потребление (новый рантайм, GPU-рендер, крупная зависимость),
согласуй с пользователем.

## Запуск

```bash
cargo run -p app -- --demo                 # без KWin/хуков, без сохранения настроек и закрытия программ
cargo run -p app -- --demo --language en
cargo run -p app -- ui goal --demo         # отдельный экран UI с тестовыми данными
cargo run -p app                           # обычный запуск: Plasma 6 или Windows
```

`--show` открывает настройки, `--background` запускает в трее. Повторный
запуск обращается к работающему экземпляру (D-Bus на Linux, именованный
мьютекс и pipe на Windows).

## Проверки

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
git diff --check
```

Кросс-проверка Windows-кода с Linux (fltk собирает C++, поэтому `ui` и `app`
не проверяются):

```bash
cargo check -p core -p platform -p daemon --target x86_64-pc-windows-msvc
```

Интеграционные тесты с реальным KWin или Win32 помечены `#[ignore]` и
запускаются вручную: `cargo test -- --ignored`. Они завершают только процессы,
которые сами запустили. Не проверяй завершение на пользовательских программах.
Headless-проверки не подтверждают реальную работу KWin и Win32 — см. `TESTING.md`.

## Сборка и локальные файлы

```bash
cargo build --release -p app
```

Релизный профиль: `lto = true`, `codegen-units = 1`, `strip = true`.
`panic = "abort"` не включать: паника в рабочем потоке должна попадать в лог,
а не молча ронять демон. Релизный тег `v<версия>` должен совпадать с `Cargo.toml`.
Не публикуй релизы и не отправляй теги без запроса пользователя.

| | Linux | Windows |
| --- | --- | --- |
| Настройки | `${XDG_CONFIG_HOME:-~/.config}/why-here/settings.json` | `%APPDATA%\WhyHere\settings.json` |
| Автозапуск | `${XDG_CONFIG_HOME:-~/.config}/autostart/org.local.WhyHere.desktop` | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\WhyHere` |
| Пункт меню | `${XDG_DATA_HOME:-~/.local/share}/applications/org.local.WhyHere.desktop` | ярлык в меню «Пуск» от установщика |

Не меняй личные настройки пользователя ради проверки: в тестах используй
временные каталоги (`XDG_CONFIG_HOME`, `APPDATA`).
Не добавляй `target/`, `dist/` и сгенерированные файлы в Git.
Обновляй оба README при изменении пользовательских команд или поведения.

Этот `AGENTS.md` предназначен для хранения в репозитории. Поддерживай инструкции
в актуальном состоянии при изменении команд и структуры проекта.
Для личных исключений используй `.git/info/exclude`, не `skip-worktree`.
