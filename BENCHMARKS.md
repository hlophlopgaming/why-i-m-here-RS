# Измерения памяти

Дата: 2026-10-15. Linux x86_64, Plasma 6 / нативный Wayland, glibc,
Rust stable; стандартный релизный профиль (LTO, один codegen-unit, strip).
База: `06ec922`, SHA-256 бинарника
`5c633a7b1456fa2bf93fadd344b0467da952b6a6f22808759159f7a9f9dfa248`.
Размер бинарника: 4 621 288 байт.

Измерение — RSS из `procps ps -o rss`, не размер виртуальной памяти и не PSS.
Каждый профиль запускается с чистым процессом три раза последовательно;
параллельно не выполняются сборки, тесты или другие бенчмарки. Первое измерение
через секунду после регистрации трея. Профиль `empty` использует настройки по
умолчанию, `full` — 64 программы и 20 целей с кириллицей. Используется отдельная
D-Bus-шина с тестовым StatusNotifierWatcher и временный XDG_CONFIG_HOME.
Нагрузка основного рабочего стола не контролируется; небольшие отличия порядка
3–5% следует считать шумом. Это локальная проверка, не гарантия RSS на каждой ОС.

UI измеряется через секунду после появления дочернего процесса; отдельного
сигнала готовности отрисовки нет, поэтому это точечный замер после запуска,
а не гарантия установившегося потребления. Затем завершается только собственный
дочерний UI, проверяется работа демона и повторно измеряется его RSS.
Дополнительно сравниваются utime/stime демона за 3 секунды простоя.
Общие действия не изменяются между проходами; benchmark находится в
`crates/app/tests/background.rs`. Для замеров скорости этот сценарий не пригоден.

```bash
cargo build --release -p app
cargo test --release -p app --test background --no-run
# Повторить три раза для каждого WHY_HERE_PROFILE=empty/full, последовательно:
FLTK_BACKEND=wayland WHY_HERE_MEASURE_MEMORY=1 WHY_HERE_PROFILE=empty \
  dbus-run-session -- cargo test --release -p app --test background -- \
  --ignored --nocapture --test-threads=1
```

виртуального размера стека не считается уменьшением RSS.

## Итог прохода

Оставлено одно изменение профиля: `opt-level = "s"`. Оно уменьшило бинарник на
30,1%, RSS демона — примерно на 7–9%. Для UI результат в пределах шума.
На проверенной машине это около 10,6 МиБ RSS демона до открытия UI и 30 МиБ
панели настроек. После закрытия UI вся память UI-процесса освобождается ОС;
RSS самого демона остаётся около 11 МиБ. **Цели 8/15 МиБ не выполнены.**

Пять независимых read-only проверок изучили память, жизненный цикл процессов,
Windows I/O, состояние UI и методику измерения, не запуская параллельных тестов
или бенчмарков. В принятом коде не найдено лишнего состояния, удаление которого
обещало бы заметное уменьшение RSS. Упрощение не требует дополнительного кода:
настройки аллокатора и менее выгодный профиль отклонены. Принудительное
сокращение строк, ограничение шрифтов, удаление функций и уменьшение резервов
стеков ради показателей не применялись. На этом безопасные небольшие изменения
сошлись; достижение оставшегося бюджета требует отдельного исследования
нативной загрузки библиотек и отрисовки с сохранением текущей архитектуры.

Оставлены изменения, убирающие повторную работу: ARGB-иконка вычисляется при
компиляции; `.desktop` разбирается без карты всех ключей; ID не клонируются для
сортировки/дедупликации; IPC сериализует срезы по 16 записей вместо клонирования
порций по 8. Windows перечисляет AppsFolder через COM вместо PowerShell;
Windows RSS и скорость каталога требуют отдельного измерения на рабочем столе.

`panic = "abort"` не включён: сохраняется изоляция паник рабочих потоков.
Объединение D-Bus не выполнено: ksni 0.3.6 создаёт соединение внутри сервиса и
не предоставляет API для общего соединения. Форк или замена трея ради
неизмеренного выигрыша в этот проход не добавлены. Отдельный диагностический
запуск после замеров обнаружил 6 потоков в `/proc/<pid>/task` до открытия UI;
его RSS не включён в таблицу. Одно число потоков не доказывает величину экономии.

Прежние жёсткие лимиты **8/15 МиБ сняты** по решению пользователя. Ориентиры —
фактические замеры, отсутствие регрессий и периодических пробуждений без сессий.
Исторические результаты выше сохранены без изменений.
